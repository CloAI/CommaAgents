# Execution Systems and Effects

Run systems provide the capabilities that surround strategy execution. Each module owns one concern for the lifetime of a prepared run and releases its resources when that run finishes, fails, is cancelled, or is discarded.

| Module | Responsibility | Client-facing surface |
|---|---|---|
| [Input](/docs/daemon/daemon-run-state/systems/input) | User-agent input collection | `request_input`, `user_input` |
| [Permission](/docs/daemon/daemon-run-state/systems/permission) | Interactive operation approval | `request_permission`, `permission_decision`, `update_policy` |
| [Question](/docs/daemon/daemon-run-state/systems/question) | Structured user questions | `request_question`, `question_response` |
| [Steering](/docs/daemon/daemon-run-state/systems/steering) | Messages queued for a live run | `steer_run`, `steer_queued` |
| [Sandbox](/docs/daemon/daemon-run-state/systems/sandbox) | Run-scoped filesystem and command boundaries | Permission requests |
| [Skills](/docs/daemon/daemon-run-state/systems/skills) | Workspace and global skill discovery | Agent skill tools |
| [MCP](/docs/daemon/daemon-run-state/systems/mcp) | MCP connections and agent tool assignment | MCP status during preparation |
| [Streaming](/docs/daemon/daemon-run-state/systems/streaming) | Agent and step events | Observation events |
| [Persistence](/docs/daemon/daemon-run-state/systems/persistence) | Run timeline recording | Run listing and continuation |
| [Sub-launch](/docs/daemon/daemon-run-state/systems/sub-launch) | Nested strategy execution | Spawned strategy results |

These modules are composed by `createDaemonRunState`; applications do not need to construct them individually.

## Choosing between a run system and a daemon effect

Use a run system for behavior that participates in strategy preparation or execution, needs run-scoped context, must be awaited in lifecycle order, or releases resources during cleanup. Persistence, streaming, permissions, input, and MCP connections belong here.

Use an internal daemon effect for synchronous observation of an already-completed run, client, or subscription transition. Diagnostic logging and metrics are examples. Effects do not replace run systems, change protocol messages, or persist execution history.

Translate external client commands in domain `DaemonService` routes, then call `DaemonRunState` or `DaemonStore`. The service registry owns parsing, validation, routing, and protocol-error conversion. WebSocket resources stay in the server, transport delivery stays in `MessageSender`, and execution-specific data stays in execution systems.

Services group inbound routes and optional effects by domain: runs, subscriptions, MCP, providers, history, Hub packages, and daemon-wide utilities. Route closures receive only their domain dependencies; WebSocket objects and a global dependency bag never enter service contracts.

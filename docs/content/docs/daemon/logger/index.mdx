# Logging

The daemon uses [LogTape](https://logtape.org/). Application startup configures logging once; services, request handlers, and run systems obtain named loggers directly. There is no per-instance logger parameter or CommaAgents logging interface.

## Startup and shutdown

`startDaemonRuntime` initializes logging before provider hydration and server creation, then closes it after the daemon stops. Imports and `createDaemon()` do not configure logging.

An embedding application can use the supplied policy:

```ts
import { initializeLogging, createDaemon, loadDaemonConfig } from "@comma-agents/daemon";

const config = loadDaemonConfig();
const logging = initializeLogging({ level: config.logLevel, file: config.logFile });
const daemon = createDaemon({ config });
try {
  await daemon.start();
  // Run the application until shutdown is requested.
} finally {
  try {
    await daemon.stop();
  } finally {
    logging.close();
  }
}
```

`initializeLogging` configures the `comma` category, so all `comma.*` loggers in the process share the policy. It refuses to replace an existing LogTape configuration. Applications already using LogTape should configure that category themselves and own disposal. Multiple daemon instances share this application policy.

## Logging from any module

```ts
import { getLogger } from "@logtape/logtape";

const logger = getLogger(["comma", "daemon", "providers"]);
logger.info("Registered provider {providerId}", { providerId: "example" });
logger.warning("Provider could not be loaded", { providerId: "example", error });
```

Logger handles can be created during module import, before configuration. Unconfigured application loggers are silent. Use stable component categories and put run IDs or client IDs in structured properties.

Native levels are `trace`, `debug`, `info`, `warning`, `error`, and `fatal`. Existing `warn` daemon configuration is accepted and mapped to `warning`; calls use `.warning()`.

## Tests without property drilling

LogTape returns the same named instance, so a test can mock a module's logger directly:

```ts
import { expect, spyOn, test } from "bun:test";
import { getLogger } from "@logtape/logtape";

test("reports a failed operation", () => {
  const error = spyOn(getLogger(["comma", "daemon", "providers"]), "error")
    .mockReturnValue(undefined);
  try {
    // Exercise the service normally, without a logger argument.
    // expect(error).toHaveBeenCalledWith(...);
  } finally {
    error.mockRestore();
  }
});
```

Instance spies mutate shared methods; use them in serial tests and restore them. For concurrent tests, use LogTape's `withConfig()` with a capture sink. Initialize a silent policy once for the suite (`initializeLogging({ stderr: false })`), then give each awaited scope its own sink:

```ts
import { withConfig, type LogRecord } from "@logtape/logtape";

const records: LogRecord[] = [];
await withConfig({
  sinks: { capture: (record) => { records.push(record); } },
  loggers: [{ category: ["comma"], lowestLevel: "debug", sinks: ["capture"] }],
}, async () => {
  // Exercise and await the service, then assert on records.
});
```

All background work under test must finish before its scope returns. Close the suite's logging owner after all scopes complete. Production initialization provides the async context storage used by these scopes.

## Migration from the custom logger

`createLogger`, `createStderrSink`, `createFileSink`, `createSystemSink`, `describeSystemLogging`, and their custom types have been removed. Configure LogTape at application startup and use its native `getLogger()` API. `createDaemon({ config })` and internal service constructors no longer accept a logger.

JSON output uses LogTape's native fields: `@timestamp`, `level`, `message`, `logger`, and nested `properties`. Levels are uppercase in JSON. Update consumers of the previous `ts`, `msg`, and `component` fields. Nested properties prevent metadata from overwriting record fields.

See [log sinks](/docs/daemon/logger/sinks) for file rotation and output behavior.

# Model

The model module handles parsing model identifiers (e.g. `openai/gpt-4o`), auto-resolving bare model IDs, maintaining a global model registry, resolving model strings into live `LanguageModel` instances, and listing providers and their available models.

## Required TEE and E2EE protection

Selecting a model that advertises TEE or E2EE support automatically requires those protections, including when you override a strategy model. E2EE also requires TEE. You do not need to add privacy flags; a default verification runtime is supplied automatically. If protection cannot be verified, the request fails without falling back to ordinary inference.

You can also declare minimum requirements explicitly:

```ts
import { createAgent, createPrivacyRuntime } from "@comma-agents/core";

const privacyRuntime = createPrivacyRuntime();
const agent = createAgent(
  {
    name: "private-researcher",
    model: "venice/your-model-id",
    privacy: { tee: "required", e2ee: "required" },
  },
  { privacyRuntime },
);
```

Tinfoil models always require TEE and E2EE, including model IDs that have not been discovered yet. Other models without advertised TEE/E2EE support use ordinary inference unless you declare requirements. Explicit requirements can strengthen protection but cannot disable advertised protections. `tee: "required"` requests independently verified hardware evidence and authenticated completion binding. Adding `e2ee: "required"` also requires encrypted conversation content; E2EE without required TEE is invalid. Requirements are checked before directly registered models or provider overrides can run. Protection is enforced for the selected provider/model identity using a trusted runtime and a supported protected provider implementation. When you request protection explicitly for a model without advertised capabilities, supply a provider/model ID and a privacy runtime. UI-added custom endpoints cannot enable it.

**Venice protected inference requires an approved serving-stack profile.** CPU and GPU evidence are independently verified. For the supported legacy dstack format, software verification replays the runtime measurement log against the authenticated RTMR3, hashes the exact application manifest, and checks its binding to MR_CONFIG_ID and the launch log. Application, OS, and key-provider identities come from that verified log. When a compose-manager attestation is present, its separate CPU quote, fresh nonce, measured guest identity, and canonical deployment-action hash must also verify.

An application supplies independently reviewed profiles through `providers.venice.trustedWorkloads`, keyed by the exact provider/model ID. Every required boot, application, key-provider, OS, and deployment measurement must match one profile. No profiles are trusted by default: missing or nonmatching approval rejects with `PRIVACY_WORKLOAD_UNTRUSTED` before inference. Missing software evidence rejects with `PRIVACY_MEASUREMENTS_UNAVAILABLE`; inconsistent evidence rejects with `PRIVACY_MEASUREMENTS_INVALID`. Do not populate approval from the response or diagnostic hashes alone.

An approved profile explicitly trusts the reviewed serving stack and pinned key-provider identity to retain private keys and enforce the GPU channel. Reports label this `gpuAssociation: "approved-workload"`; they do not claim independently proven physical CPU/GPU co-location or model-weight provenance. Missing GPU evidence still rejects. The ACI gateway format requires additional keyset, custody, and upstream-session verification and is not supported by this legacy verifier. By default, completion signatures must authenticate the request and response before output is released.

Text and tool calling are the supported core input categories. Each protected provider must establish coverage for the requested combination. Venice E2EE encrypts every normalized conversation message, including assistant history and local tool data. System instructions and tool definitions are combined before encryption so the request carries one encrypted system message. Tool definitions, assistant tool requests, and tool results stay inside encrypted message content. Decrypted tool requests are converted into local tool calls after response authentication. Tool selection and parallel-call settings are enforced locally. Flattened tool arguments are normalized only when every input field is declared by the offered tool; input schema validation still runs before execution. Malformed or unoffered calls reject. Structured output remains unsupported. Multimedia is outside this API. There is no automatic downgrade to ordinary inference.

For direct model callers, use the same runtime and requirements. The example loads a locally maintained file of independently reviewed profiles; it must not be generated from the live attestation:

```ts
import { readFile } from "node:fs/promises";
import { createPrivacyRuntime, resolveModel } from "@comma-agents/core";
import type { VeniceWorkloadPolicy } from "@comma-agents/core";

const trustedWorkloads = JSON.parse(
  await readFile("./reviewed-venice-profiles.json", "utf8"),
) as Record<string, VeniceWorkloadPolicy[]>;
const privacyRuntime = createPrivacyRuntime({
  providers: { venice: { trustedWorkloads } },
  onEvent(event) {
    console.log(event.phase, event.report?.errorCode);
  },
});
const model = await resolveModel("venice/your-model-id", {
  privacy: { tee: "required", e2ee: "required" },
  privacyRuntime,
  onPrivacyReport(report) {
    console.log(report.status, report.checks);
  },
});
```

The trusted endpoint is the process running core. Local hooks, tool execution, and conversation history retain plaintext behavior. This feature does not encrypt browser-to-daemon traffic, local history, or independent network calls made by tools. Built-in summarization inherits the agent's requirements; custom summarizer callbacks and custom execution overrides are rejected for protected agents.

Each upstream request has independent verification, cancellation, and encryption context ownership, including tool steps. Venice and Tinfoil V3 use client-generated attestation challenges; Tinfoil also enforces authenticated freshness-witness expiry. The application does not retry protected inference automatically. Tinfoil can reverify and resend once after its transport reports a stale encryption key; ordinary inference failures are not retried. Output is buffered until required authentication passes, including tool calls before execution. Cancellation, truncated streams, failed checks, or conflicting provider options discard unreleased output. Observer callbacks are synchronous; callback exceptions reject the request.

Runtime defaults are a 120-second request deadline, 15 seconds per verification operation within that deadline, a 2 MiB evidence-response limit, 64 MiB of buffered inference wire data, and 16 MiB of decrypted completion data. Override them through `limits`; verification endpoints must be trusted HTTPS addresses supplied by the application. Venice never follows endpoint addresses from attestation payloads. Tinfoil verifies nonce-bound V3 evidence from its fixed inference endpoint and encrypts to the HPKE key endorsed by that evidence.

Content-free reports contain request identity, requirements, check outcomes, timestamps, and safe failure codes. Agent results retain per-request `privacyReports`, including summarization. Direct model results expose successful report metadata under `commaPrivacy`. No report includes prompts, raw evidence, keys, or underlying provider exception bodies. Hardware verification alone does not approve an application. `workloadMeasurements` reports authenticated software hashes, while `checks.workload` reports profile approval. Passed CPU/GPU, freshness, and key-binding checks remain visible after a later rejection. A workload approval rejection includes `workloadMismatch`, showing differing fields and their expected/actual values for each approved profile, or indicating that no profiles were configured. Profile approval does not verify model weights or the correctness of model output. Venice reports also include independent `receiptChecks` for the completion ID, signature under the attested key, signed model prefix when present, and exact request/response body hashes. A valid signature can coexist with failed body binding; missing or malformed receipt evidence is reported as unavailable. Required receipt failures reject by default; the explicit body-binding exception below allows degraded output.

## Tinfoil protected inference

Set `TINFOIL_API_KEY` or save a Tinfoil credential in provider settings, refresh the model list, and select a `tinfoil/model-id`. Protection is automatic, including strategy overrides and summarization. An approved Venice workload file is not needed.

```ts
import { createAgent } from "@comma-agents/core";

const agent = createAgent({
  name: "private-assistant",
  model: "tinfoil/glm-5-3",
});
const result = await agent.call("Hello");
```

Tinfoil V3 verifies AMD Genoa SEV-SNP CPU evidence, the request nonce, signed code and platform provenance, policy/measurement matches, certificate and revocation validity, and freshness witnesses. The attested HPKE key must be bound to those same authenticated measurements. Requests and responses use authenticated encryption tied to a separate request context. The complete request body is encrypted, including system instructions, chat history, native tool definitions, tool arguments, and tool results. Local tools execute after completion authentication; streaming output is buffered until authentication and parsing finish.

**The first-party V3 verifier is experimental and has not had an independent security audit.** It supports the public router's release-based collateral profile on AMD Genoa, with pinned manufacturer and Sigstore trust roots. Intel TDX, AMD Turin, device/GPU evidence, registry-based collateral, and legacy V2 evidence are rejected. No unmerged verifier PR or Go runtime is required. A change to the supported evidence profile or pinned trust material requires a reviewed verifier update.

Reports mark `cpu`, `workload`, `freshness`, `keyBinding`, `encryption`, and `responseBinding` as passed after successful verification and authenticated inference. `workloadMeasurements` includes the authenticated launch measurement and code/platform digests. `freshnessExpiresAt` records the authenticated authorization deadline. Nonces are fresh for each attestation; code/platform witnesses have a separate maximum age of seven days by default. Expired evidence prevents inference and output release. `verificationSteps` reports V3 success or the failing verification boundary without raw evidence or provider errors.

Clients verify the router's published workload and trust that measured router to validate downstream model enclaves. This integration does not independently verify each GPU or exact model weights; `gpu` remains `unavailable`. No Venice receipt exception applies. Missing HPKE keys, failed V3 checks, plaintext responses, authentication failures, and resource-limit failures reject the request. One recognized stale-key rejection can trigger fresh V3 verification and resealing; ordinary inference failures are not retried. Header and routing metadata remain visible to the transport.

Use application-owned policy to pin a reviewed repository/release, add a launch-measurement constraint, or require more recent witnesses. Default approval follows valid, currently witnessed releases from `tinfoilsh/confidential-model-router`; it does not automatically require the newest release. `reference` also accepts `owner/repo@tag`, `owner/repo@sha256:<digest>`, or both constraints. Additional measurement pins are checked alongside signed policy. Never approve measurements solely because the endpoint reports them.

```ts
import { createAgent, createPrivacyRuntime } from "@comma-agents/core";

const privacyRuntime = createPrivacyRuntime({
  providers: {
    tinfoil: {
      reference: "tinfoilsh/confidential-model-router",
      freshnessMaxAgeMs: 24 * 60 * 60 * 1000,
    },
  },
});
const agent = createAgent(
  { name: "private-assistant", model: "tinfoil/glm-5-3" },
  { privacyRuntime },
);
```

To continue when an authentic receipt covers body hashes that do not match the public API exchange, explicitly enable `allowUnboundReceipts`:

```ts
const privacyRuntime = createPrivacyRuntime({
  providers: { venice: { trustedWorkloads, allowUnboundReceipts: true } },
});
```

This trusts the provider path without establishing integrity of the exact conversation or encrypted-chunk ordering. It also permits local tool calls from those accepted responses. Reports use `status: "degraded"`, retain `responseBinding: "failed"`, and include `PRIVACY_BINDING_UNAVAILABLE`. Invalid signatures, completion IDs, signed model IDs, malformed receipt hashes, and hardware or workload failures still reject. The default is `false`; the exception applies only to body-hash mismatches.

## How Model Resolution Works

The ordinary resolution order below applies when neither advertised capabilities nor explicit requirements demand privacy protection. Protected requests enforce their requirements before consulting directly registered models or the global provider resolver.

When `createAgent()` receives a model string, `resolveModel()` resolves it into a live `LanguageModel`. Two formats are supported:

1. **Explicit** `"providerID/modelID"` — e.g. `"openai/gpt-4o"`. The provider is used directly.
2. **Bare model ID** — e.g. `"gpt-4o"`. The model catalog is queried to find all providers that list the model. Each candidate provider is checked for configured credentials; the first one with a matching credential wins.

Resolution order for both formats:

1. **Direct model registry** — exact match via `registerModel()`. Ideal for tests and mocking. Checked first, before any parsing or catalog lookup.
2. **Explicit provider** (contains `/`) — parses the string into provider/model parts, looks up credentials via the global credential store, then creates a `LanguageModel` via the global provider resolver.
3. **Auto-resolution** (no `/`) — queries the reverse model index for candidate providers (sorted alphabetically), checks credentials for each candidate, and resolves the first one with configured credentials.

```ts
import {
  registerModel,
  registerProvider,
  createAgent,
} from "@comma-agents/core";

// Option 1: Register a model directly (great for tests)
registerModel("mock/test", myMockLanguageModel);
const agent = createAgent({ name: "test", model: "mock/test" });

// Option 2: Register a provider (for custom/non-standard providers)
registerProvider("my-llm", {
  factory: (credential) => (modelId) =>
    myProvider({ apiKey: credential.key, model: modelId }),
});
const agent2 = createAgent({ name: "custom", model: "my-llm/latest" });

// Option 3: Known providers resolve automatically (openai, anthropic, etc.)
// Just ensure credentials are configured and the provider's npm package is installed.
const agent3 = createAgent({ name: "writer", model: "openai/gpt-4o" });

// Option 4: Bare model ID — auto-resolves provider from catalog
// The first provider with credentials for "gpt-4o" wins
const agent4 = createAgent({ name: "assistant", model: "gpt-4o" });
```

When no provider has credentials for a bare model ID, `resolveModel` throws a `ModelResolutionError` listing all providers that support the model, so you know exactly which credentials to configure.

## Model Registry

### registerModel

Register a `LanguageModel` instance for a specific model string. Registered models take precedence over provider-based resolution.

```ts
import { registerModel } from "@comma-agents/core";

registerModel("mock/test", mockLanguageModel);
```

### unregisterModel

Remove a previously registered model. Returns `true` if it was registered and removed.

### resetModelRegistry

Reset the global model registry to empty state. Primarily for tests.

## Model Metadata Lookup

Query the catalog for metadata about a specific model by its bare ID.

### getModelMetadata

Returns full `ModelInfo` for a bare model ID — capabilities, modalities, cost, context window, and more. The catalog is checked for the first provider that lists the model.

```ts
import { getModelMetadata } from "@comma-agents/core";

const info = getModelMetadata("gpt-4o");
console.log(info?.contextWindow); // 128000
console.log(info?.capabilities?.reasoning); // true
console.log(info?.cost?.input); // 2.5 (USD per 1M tokens)
```

Returns `undefined` if the model is not found in any provider catalog.

### getModelCapabilities

Convenience wrapper for checking capability flags. Returns `ModelCapabilities | undefined` for a bare model ID.

```ts
import { getModelCapabilities } from "@comma-agents/core";

const caps = getModelCapabilities("gpt-4o");
if (caps?.reasoning) {
  // Use reasoning-related provider options
}
if (caps?.vision) {
  // Send image inputs
}
```

## Provider Resolution

Providers are resolved via `registerProvider()` in the [defaults](/docs/core/defaults) module. The global provider resolver checks:

1. Custom provider registrations (via `registerProvider()`)
2. Built-in overrides (e.g. `ollama`, `deepseek`, `github-copilot`)
3. The bundled provider catalog, which maps each provider id to its npm package
4. Last resort: attempt a dynamic import for the provider package

## Provider Discovery

The model module also exposes APIs to list known providers and their models. Data comes from three sources merged together:

- **Catalog** — a bundled snapshot of the [models.dev](https://models.dev) catalog, covering 50+ providers and their models. The snapshot is shipped with the package and refreshed on disk every 24 hours.
- **Built-in overrides** — hardcoded entries for providers that need custom package resolution or their own model lister (Ollama, Deepseek, GitHub Copilot).
- **Provider APIs** — model lists from supported providers, kept in memory after `refreshProviderModels()` calls them.
- **User settings** — manually declared models are always included.

Models are identified within their provider. Results include the union of provider, models.dev, and user IDs, sorted alphabetically. Each model has `id`, contributing `sources`, and nested `metadata`. Fields resolve with priority provider > models.dev > user, including individual capability and pricing fields. Explicit `false`, zero, and empty modality arrays retain their meaning. Providers expose their definition `origin`.

All existing capabilities are supported: tools, reasoning, vision, attachment, structured output, TEE attestation support, and E2EE support. Privacy support flags describe advertised capabilities; request requirements and verification reports remain separate.

### listProviders

Return every known provider enriched with its model list. Listing never calls a provider API; it includes the provider-listed models from the last `refreshProviderModels()` call.

```ts
import {
  getGlobalCredentialStore,
  listProviders,
  refreshProviderModels,
} from "@comma-agents/core";

// Call every provider's own model listing, then read the merged list.
await refreshProviderModels(getGlobalCredentialStore());
const providers = await listProviders(getGlobalCredentialStore());
for (const provider of providers) {
  console.log(provider.id, provider.models.length);
}
```

### refreshProviderModels

Call provider APIs and keep their model lists in memory. Pass `{ providerId }` to refresh one provider. A provider is called only when it has a lister and, unless its `credentialType` is `"none"`, a resolved credential. A failed or empty response drops that provider's previous listing, leaving models.dev and manual models.

### getProviderInfo

Fetch information for a single provider by id.

```ts
import { getGlobalCredentialStore, getProviderInfo } from "@comma-agents/core";

const info = await getProviderInfo("openai", getGlobalCredentialStore());
console.log(info?.name, info?.models[0]?.id);
```
